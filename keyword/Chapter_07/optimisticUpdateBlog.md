# **낙관적 업데이트(OptimisticUpdate)**를 왜 도입해야 하는지, 이 패턴이 해결하려는 문제를 실제 서비스 맥락에서 설명해보세요.
    
    ### 1. 낙관적 업데이트(Optimistic Update)를 왜 도입해야 할까?
    
    낙관적 업데이트는:
    
    > “서버 응답을 기다리지 않고 성공할 것이라 가정한 뒤, UI를 먼저 변경하는 방식”
    > 
    
    입니다.
    
    보통 서버 요청은 네트워크 상황에 따라:
    
    - 수백 ms ~ 수 초까지 걸릴 수 있습니다.
    - 모바일 환경에서는 더 느려질 수도 있습니다.
    
    만약 모든 UI 변경을 서버 응답 이후에 처리하면:
    
    ```
    버튼 클릭
    → 로딩
    → 서버 응답 대기
    → UI 변경
    ```
    
    흐름이 되면서 사용자는 앱이 느리다고 느끼게 됩니다.
    
    ---
    
    실제 서비스 예시로 “좋아요” 기능을 생각해보면:
    
    ### 일반 방식
    
    ```
    좋아요 클릭
    → 서버 요청
    → 응답 성공
    → 하트 색 변경
    ```
    
    이 경우 네트워크가 느리면 사용자는:
    
    ```
    “클릭이 안 된 건가?”
    ```
    
    라고 느껴 여러 번 누를 수도 있습니다.
    
    ---
    
    ### 낙관적 업데이트 적용
    
    ```
    좋아요 클릭
    → 하트 즉시 변경
    → 서버 요청
    → 실패 시 롤백
    ```
    
    이렇게 되면 사용자는:
    
    ```
    “앱이 빠르고 반응성이 좋다”
    ```
    
    라고 느끼게 됩니다.
    
    즉 낙관적 업데이트는:
    
    - 사용자 체감 속도 개선
    - 인터랙션 반응성 향상
    - 로딩 스트레스 감소
    - 부드러운 UX 제공
    
    문제를 해결하기 위해 도입합니다.
    
    특히:
    
    - 좋아요
    - 북마크
    - 체크박스
    - 댓글 작성
    - ToDo 추가
    
    처럼 성공 확률이 높은 액션에서 매우 효과적입니다.
    
# TanStack Query 기반 구현 흐름을 `onMutate → (mutate) → onError → onSettled` 순서로 기술해주세요.
    
    TanStack Query의 낙관적 업데이트는 보통:
    
    ```
    onMutate
    → mutate 실행
    → onError
    → onSettled
    ```
    
    흐름으로 동작합니다.
    
    ---
    
    ## ① onMutate
    
    서버 요청이 실제로 보내지기 “직전” 실행됩니다.
    
    여기서:
    
    - 기존 캐시 저장
    - 낙관적 UI 업데이트
    - 진행 중인 refetch 취소
    
    등을 수행합니다.
    
    예시:
    
    ```
    onMutate:async (newTodo) => {
    awaitqueryClient.cancelQueries(['todos'])
    
    constpreviousTodos=
    queryClient.getQueryData(['todos'])
    
    queryClient.setQueryData(['todos'], (old) => [
        ...old,
    newTodo
      ])
    
    return { previousTodos }
    }
    ```
    
    즉:
    
    ```
    기존 상태 백업
    → UI 먼저 수정
    ```
    
    단계를 담당합니다.
    
    ---
    
    ## ② mutate 실행
    
    이후 실제 서버 요청이 실행됩니다.
    
    ```
    POST /todos
    ```
    
    같은 API 호출 단계입니다.
    
    이 시점에서는 이미 UI가 변경되어 있으므로
    
    사용자는 즉각적인 반응을 느끼게 됩니다.
    
    ---
    
    ## ③ onError
    
    서버 요청 실패 시 실행됩니다.
    
    여기서는:
    
    - 이전 상태로 롤백
    - 에러 메시지 표시
    
    등을 처리합니다.
    
    예시:
    
    ```
    onError: (error,newTodo,context) => {
    queryClient.setQueryData(
        ['todos'],
    context.previousTodos
      )
    }
    ```
    
    즉:
    
    ```
    실패
    → 이전 캐시 복구
    ```
    
    역할입니다.
    
    ---
    
    ## ④ onSettled
    
    성공/실패 여부와 관계없이 마지막에 실행됩니다.
    
    보통:
    
    ```
    queryClient.invalidateQueries(['todos'])
    ```
    
    를 통해 서버 데이터를 다시 동기화합니다.
    
    즉:
    
    ```
    최종적으로 서버 기준 데이터 재검증
    ```
    
    단계입니다.
    
# ToDo “생성” 및 “좋아요 토글”에 **낙관적 업데이트(OptimisticUpdate)**를 적용했을 때의 **실패/충돌 롤백 전략**을 설계해주세요.
    
    ToDo 생성은:
    
    ```
    새로운 데이터 추가
    ```
    
    상황입니다.
    
    ---
    
    ## 낙관적 업데이트 흐름
    
    ### 1단계
    
    사용자가 “할 일 추가” 클릭
    
    ### 2단계 - onMutate
    
    임시 Todo를 캐시에 먼저 추가
    
    예시:
    
    ```
    {
    id:Date.now(),// 임시 id
    title:'공부하기',
    pending:true
    }
    ```
    
    UI에는 즉시 표시됩니다.
    
    ---
    
    ## 실패 시 롤백 전략
    
    만약 서버 요청 실패:
    
    ```
    POST /todos 실패
    ```
    
    라면:
    
    ### 방법 1. 이전 캐시 복구
    
    ```
    context.previousTodos
    ```
    
    로 전체 롤백
    
    가장 안전한 방식입니다.
    
    ---
    
    ### 방법 2. 임시 Todo만 제거
    
    임시 ID 기반으로 제거:
    
    ```
    filter(todo =>todo.id!==tempId)
    ```
    
    이 방식도 많이 사용됩니다.
    
    ---
    
    ## 충돌 상황 고려
    
    예를 들어:
    
    - 사용자가 연속으로 여러 개 생성
    - 서버 응답 순서가 꼬임
    
    상황이 생길 수 있습니다.
    
    이 경우:
    
    ```
    임시 ID(tempId)
    ```
    
    를 별도로 관리해서:
    
    ```
    임시 데이터 ↔ 실제 서버 데이터
    ```
    
    를 정확히 매핑해야 합니다.
    
    ---
    
    # 4. 좋아요 토글 낙관적 업데이트 롤백 전략
    
    좋아요는:
    
    ```
    boolean 상태 변경
    ```
    
    이라 비교적 단순합니다.
    
    ---
    
    ## 낙관적 업데이트 흐름
    
    현재 상태:
    
    ```
    liked: false
    likeCount: 10
    ```
    
    사용자 클릭 시 onMutate에서:
    
    ```
    liked: true
    likeCount: 11
    ```
    
    로 즉시 변경
    
    ---
    
    ## 실패 시 롤백 전략
    
    서버 실패 시:
    
    ```
    liked: false
    likeCount: 10
    ```
    
    으로 원복합니다.
    
    즉 이전 상태 snapshot을 저장해두고 복구하는 방식입니다.
    
    ---
    
    ## 충돌 상황 고려
    
    좋아요는 동시성 문제가 자주 발생합니다.
    
    예를 들어:
    
    ```
    사용자 A 좋아요
    사용자 B 좋아요
    ```
    
    가 동시에 발생하면:
    
    클라이언트 숫자와 서버 숫자가 달라질 수 있습니다.
    
    ---
    
    그래서 보통:
    
    ```
    onSettled: () => {
    invalidateQueries(['post',id])
    }
    ```
    
    로 최종적으로 서버 데이터를 다시 가져옵니다.
    
    즉:
    
    ```
    낙관적 업데이트 = UX 개선용
    최종 정합성 = 서버 refetch로 보장
    ```
    
    전략을 사용합니다.
