# 낙관적 업데이트(OptimisticUpdate)가 효율적인 상황은 언제일까요? 

낙관적 업데이트는

“서버 응답을 기다리지 않고, 성공할 것이라고 가정한 뒤 UI를 먼저 변경하는 방식”입니다.

즉:

```
사용자 액션
→ UI 먼저 변경
→ 이후 서버 요청
→ 실패하면 롤백
```

흐름이에요.

---

효율적인 상황은 보통:

> “실패 가능성이 낮고, 사용자 반응 속도가 중요한 기능”
> 

입니다.

예시:

- 좋아요 버튼
- 북마크
- 댓글 좋아요
- 체크박스 토글
- 간단한 설정 변경
- 할 일 완료 체크

같은 기능들이 대표적이에요.

예를 들어 좋아요 버튼에서:

```
클릭
→ 하트 바로 빨개짐
→ 서버 요청
```

이렇게 동작하면 사용자는:

```
“앱이 빠르고 부드럽다”
```

라고 느끼게 됩니다.

반대로 서버 응답을 기다리면:

```
클릭
→ 0.5초 대기
→ 하트 변경
```

처럼 느려 보일 수 있어요.

---

또 낙관적 업데이트는:

- 요청 성공률이 높고
- 데이터 충돌 가능성이 낮고
- UI 변화가 단순한 경우

특히 효과적입니다.

예를 들어:

```
좋아요 true ↔ false
```

처럼 상태 하나만 바뀌는 경우는

롤백도 쉽고 관리도 단순해요.

# 낙관적 업데이트(OptimisticUpdate)를 피해야 하는 상황 언제일까요?
반대로:

> “실패 가능성이 높거나, 데이터 정합성이 중요한 경우”
> 

에는 조심해야 합니다.

대표적인 예시:

- 결제
- 송금
- 재고 차감
- 좌석 예약
- 주문 처리
- 포인트 사용
- 금융 데이터 수정

같은 기능이에요.

---

예를 들어 좌석 예약에서:

```
사용자가 좌석 선택
→ UI에서 바로 예약 완료 표시
→ 실제 서버에서는 이미 다른 사람이 선점
```

이라면 사용자 경험이 오히려 혼란스러워집니다.

즉:

```
“예약된 줄 알았는데 실패함”
```

상황이 생기는 거예요.

---

또 낙관적 업데이트는 롤백 처리가 필요합니다.

예를 들어:

```
UI 먼저 수정
→ 서버 실패
→ 이전 상태로 복구
```

를 해야 하는데,

복잡한 데이터 구조에서는:

- 롤백 로직이 어려워지고
- 상태 꼬임이 발생할 수 있어요.

특히:

- 여러 캐시가 연결되어 있거나
- 서버 계산 결과가 중요하거나
- 다른 사용자와 실시간 충돌이 가능한 경우

에는 오히려 유지보수가 어려워질 수 있습니다.

### 낙관적 업데이트를 피해야 하는 경우

- 데이터 정합성이 매우 중요함
- 실패 비용이 큼
- 서버 검증이 핵심임
- 동시성 충돌 가능성이 큼
- 롤백이 복잡함

예시:

- 결제
- 송금
- 예약
- 재고 관리
- 주문 처리

즉 핵심은:

> “조금 틀려도 UX가 중요한 기능”에는 낙관적 업데이트가 좋고,
> 
> 
> “절대 틀리면 안 되는 데이터”에는 신중해야 한다
> 

---

# 정리

### 낙관적 업데이트가 좋은 경우

- 실패 확률이 낮음
- 즉각적인 반응이 중요함
- UI 변화가 단순함
- 롤백이 쉬움

예시:

- 좋아요
- 북마크
- 토글
- 체크 처리
